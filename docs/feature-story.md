# 当 Skill 学会节省上下文：一个 AI 管理员的自述

> 如果把每个 AI Skill 都看作一名专家，过去的做法是让所有专家站在会议室里；`skill-router` 的想法是，只让接待员站在门口。

## 一、问题从“技能太多”开始

AI Agent 的插件和 Skill 正在变得像手机应用一样丰富。

写文档有文档 Skill，读 PDF 有 PDF Skill，做表格有表格 Skill，处理视频有视频 Skill。每一种能力都值得拥有，但每一种能力都带着自己的说明。

问题在于：模型并不需要每个请求都认识所有专家。

当用户只是问“今天几号”，上下文里却背着几十个 Skill 的触发说明；当用户明确说要处理 PDF，系统仍然可能先阅读一堆无关的自动化描述。

这不是某个 Skill 的问题，而是 Skill 生态成熟后的结构性问题。

`skill-router` 的第一句设计原则由此诞生：

**先判断任务，再决定 Skills。**

## 二、不是分类器，而是闸门

很多工具会把自己定位成“Skill 推荐器”。

`skill-router` 更像一道闸门。

用户提出任务后，它先检查任务是否足够清楚。如果目标、输入、输出、目标环境或验收条件缺失，它不会急着扫描 Skill，而是先问问题。

这一步看似朴素，却直接改变了下游行为：

- 不会为模糊任务误选 Skill
- 不会因为理解偏差而执行错误流程
- 不会把真正需要的确认留给事后补救

任务清楚后，闸门才打开。

接下来是 provider 检测、聚焦扫描、候选排序和置信度判断。置信度高时继续；置信度不足时，列出 2–5 个候选，把选择权交还给用户。

这与“自动替用户做所有决定”不同。它把确定性交给系统，把真正的分歧交给人。

## 三、最亮眼的不是路由，而是上下文预算

Skill 路由只是第一层。

第二层问题更隐蔽：即使只有一个 Skill 被选中，它仍然可能拖着大量参考文档进入上下文。

`context_budget.py` 解决的是“每轮都带大量无关 Skill 描述”的问题。

它把非路由类 Skill 设置为用户调用，让它们的描述退出常驻上下文。只有在 `skill-router` 真的需要时，才会按路径读取对应 Skill。

在 Codex 环境中，这套策略估算每轮减少约 `9.6k` 上下文 token。

这不是简单地删资料，而是改变资料的进入时机。

## 四、Context Compiler：让文档按问题展开

节省 token 不等于牺牲能力。

`skill_context.py` 是这套系统里的“上下文编译器”。它会根据当前任务，生成一个 query-scoped context pack：

- 加载和任务相关的章节
- 保留高价值的安全与工作流段落
- 列出 reference 索引
- 给出被省略章节的行号
- 标注 token 估算

这像记者采访前准备资料包：先带最相关的材料进现场，需要时再回到档案库。

对于大型 Skill，例如视频平台工程、论文写作或 API 安全，第一次只加载全部文档会非常昂贵。Context Pack 让“开始工作”与“阅读全部资料”分离。

## 五、让经验可验证，而不是神秘地“变聪明”

很多系统会说自己在自我进化。

但真正的进化不能只是让模型改写提示词，然后期待它变得更好。

`skill-router` 采用更克制的路径：

1. 记录真实任务的经验。
2. 标记失败点、修正和证据。
3. 生成 Skill 能力画像。
4. 把重复模式转成候选更新。
5. 运行 practice suite。
6. 比较升级前后的通过率、耗时和输出 token。
7. 验证通过才应用。
8. 同步到多个 provider，并保留快照和回滚点。

`experience_store.py` 负责经验记录。

`practice_runner.py` 负责练习和版本比较。

换句话说，Skill 的成长不是“我改了自己”，而是“我经历了这些任务，留下这些证据，通过了这些测试，然后才改变”。

## 六、跨模型厂商的统一管理员

不同工具提供不同 Skill 目录：

- Claude
- OpenCode
- Codex
- Cursor
- Gemini
- Windsurf
- 自定义 provider

`skill-router` 不假设所有 Skill 都住在同一个地方，而是通过 provider root 发现、扫描、验证和同步。

这带来一个直接结果：同一个 Skill 可以在不同环境中保持一致，而不是在每个平台各自漂移。

## 七、它最特别的地方

如果只看功能列表，它像一组工具：

- 扫描
- 路由
- 预算
- 编译
- 记录
- 练习
- 验证
- 同步

但真正特别的是这些工具背后的顺序：

**先澄清任务，再路由；先最小扫描，再加载；先记录证据，再升级；先验证，再同步。**

这是一种把 AI 能力管理当作工程系统来做的思路。

## 八、边界同样重要

`skill-router` 不自动绕过权限，不自动处理未授权内容，也不因为“自动化”而跳过安全判断。

高风险变更、权限扩展、删除操作和未验证来源会停在待批准状态。

这使它的进化能力保持可审计、可解释、可回滚。

## 九、下一步

这个项目仍然在快速迭代。

未来最值得继续推进的方向包括：

- 更准确的 Skill 选择评分
- 更细粒度的上下文预算 profile
- 跨 provider 的经验聚合
- 自动生成 practice suite
- 基于 scorecard 的晋升策略
- 更直观的可视化报告

但它已经证明了一件事：

AI 的能力增长，不一定意味着每轮请求都要携带更多资料。

有时候，真正的进步是让系统知道：

**什么时候该看，什么时候不该看，什么时候只需要看一半。**
